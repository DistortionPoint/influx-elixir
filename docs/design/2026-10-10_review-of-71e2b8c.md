## Problem

Each defect was reproduced before it was changed, against InfluxDB 3 Core 3.10.1 (`localhost:8181`) or
InfluxDB 2.7.12 (the one-liners in `README.md`).

### F1: Flight reads FlatBuffer defaults as if they were set

FlatBuffers leave out a field that holds its schema default, and `Schema.fbs` defaults `Int.is_signed`
and `Int.bitWidth` to 0/false and `FloatingPoint.precision` to HALF. The reader had `is_signed`
absent = signed and precision absent = double.

| Statement | HTTP | Flight before |
|---|---|---|
| `arrow_cast(200,'UInt8')`, `60000` UInt16, `3000000000` UInt32, `10000000000000000000` UInt64 | 200, 60000, 3000000000, 10000000000000000000 | -56, -5536, -1294967296, -8446744073709551616 |
| field `u=18446744073709551615u` | 18446744073709551615 | -1 |
| `arrow_cast(1.5,'Float16') a, 2 c` | `a` = 1.5, `c` = 2 | `[%{"c" => 2}]` (the column dropped) |

The audit of every other FlatBuffer read: the Timestamp unit (absent = second), Duration unit (absent =
millisecond), Date unit (absent = millisecond, Date64), Decimal `bitWidth` (absent = 128; scale and
precision 0), FixedSizeList `listSize` (0), Field `type_type` (NONE), dictionary, children and the
Message header type were already right, and are now commented as defaults. The audit found two more
differences from HTTP, both fixed:

- A Float32 (and Float16) is printed by HTTP as the shortest decimal that reads back as the same 32
  bits (`0.1`); Flight gave the double of the bits (`0.10000000149011612`).
- A Date64 is a datetime string over HTTP (`1970-01-02T00:00:00.500`, which `ResponseParser` reads as
  a `DateTime`); Flight gave a date. An infinity or a NaN is `null` over HTTP (a key that is present,
  where a null cell has no key); Flight dropped the cell and, for a Float64, shifted the values after
  it (a comprehension skips what a float pattern does not match).

### F2: `\\` is one backslash on InfluxDB 3 and two on 2.7

`LineProtocol.encode` escaped a backslash in measurements, tag keys and values and field keys. InfluxDB 3
reads `\\` as one backslash (12 strings round-tripped on Core); 2.7's parser never unescapes it in a
name. Tag value `a\b` was stored on 2.7 as `a\\b`. 25 strings in five positions (measurement, tag key,
tag value, field key, string field value) were written to 2.7.12 and read back through Flux:

- 2.7 undoes a backslash only before a character the position escapes: in tag keys and values `,` `=`
  and space; in measurements and field keys those and `"`. A backslash before any other character, or
  before another backslash, is kept as written.
- A measurement written with `\=` or `\"` is stored (`schema.measurements` lists it) but no
  `range()` query returns its points, and plain `=` or `"` in a measurement works. So a measurement
  escapes only `,` and space.
- A measurement with a backslash before `,`, space, `=` or `"`, and a field key with one before `,`,
  space or `=`, cannot be kept: the points are unqueryable, or the write is a 400 (`invalid field
  format`, the scanner takes `\\` as a pair and the next `,` as the end of the field set). No encoding
  of those names reads back as written.
- A string field value escapes `\` and `"`, as on v3.

`Client.Local`'s `:v2` table (`LineProtocolEscape`) already matched all of it: the same 25 × 5 strings
gave the same answers on 2.7 and on Local.

### F3 (encoding): `Point.new` and `LineProtocol.encode` raised

`Point.new("m", f, tags: nil)` and `Point.new("m", nil)` raised in `Enum.sort_by(nil)` or `map_size(nil)`;
`encode(:x)`, `encode([%{}])` and `encode(point, :notkw)` raised.

### F6: Flight `:timeout` was a request header

A TCP peer that accepts and stays silent held `Flight.Client.query/3` for the gRPC library's wait (5 s;
60 s until the peer closed), whatever `:timeout` said. `Client.HTTP` passed only the call's `:timeout`,
never the connection's. A failed query was a `%GRPC.RPCError{}`, where HTTP gives
`%{status: _, body: _}`. An empty token sent `Authorization: Bearer `. The ticket payload was built
twice.

### F8: HTTP and `QueryParams` raised on what a caller passes

No Finch pool of that name: `ArgumentError: unknown registry`; a keyword connection without `:name`
or `:finch_name`: `KeyError`; a parameter that is an improper list or has a tuple map key: Jason
raised; `InfluxElixir.query_sql("hostname", ...)` raised in the telemetry span (`"hostname"[:database]`);
`query_influxql(..., format: nil)` sent `"format": ""` and got a 400.

### F10: Local's v2 unescape was quadratic

`unescape_v2/3` rebuilt `<<c, rest::binary>>` for each backslash before a character that is no escape,
copying the rest of the text: 200,000 of them (a `\x` repeated in one tag value) took 1.05 s.

## Design

- **Reader.** `resolve_type_id` reads `bitWidth` absent as 0, `is_signed` absent as false, and
  `precision` absent as HALF, which has no type id and decodes as the `:float16` kind. Half precision is
  decoded from its bits (sign, 5-bit exponent, 10-bit fraction; subnormals as fraction × 2^-24; exponent 31
  is infinity or NaN). Float16 and Float32 go through `shortest32/1` (the fewest digits, 1 to 9, that
  read back as the same 32 bits). An infinity or NaN cell is the atom `:non_finite` until `zip_columns/3`
  writes it as `nil`, and inside a list as `nil`. Float64 columns keep the single-pass comprehension and
  are read again by bits only when it skipped a cell. Date64 is a `DateTime`.
- **LineProtocol.** `encode/2` takes `api_version: :v3 | :v2` (default `:v3`); it validates its options and
  its argument first and answers `{:invalid_options, opts}` / `{:invalid_point, term}`. Escape kinds per
  dialect are a table (`@kinds`); the names 2.7 cannot keep are listed beside it, per position
  (`measurement_refuses`, `field_key_refuses`), and refused with the existing error shapes. The alternative,
  writing them anyway, stores different text silently on a `204`. `BatchWriter` reads the connection's
  `api_version` per `Point` through the new `Connection.api_version/1` (a name, a keyword list or a
  `Client.Local` connection).
- **Point.new.** `nil` fields and tags are empty (the spec says so).
- **Flight.Client.** The call and the collecting of its stream run in one monitored, unlinked process
  (the adapter delivers the stream to the process that made the call) under the generalised `bounded/4`,
  also used by `bounded_connect/2`; past `:timeout` it is killed and the answer is `{:error, :timeout}`,
  and the channel is closed by the caller. A gRPC error is `%{status: http_status, body: message}`:
  3 → 400, 16 → 401, 7 → 403, 5 → 404, 6 → 409, 8 → 429, 12 → 501, 14 → 503, 4 → `:timeout`, others 500. Verified with the same
  statements over both transports on Core: a syntax error, an unknown table, an empty statement and DDL
  are 400 on both; a schema error (`SELECT nosuch FROM m`) is 500 over HTTP and gRPC 3 (400) over Flight; a
  database that does not exist is 404 over HTTP and gRPC 13 (500) over Flight; Flight's message keeps
  `Error while logically planning query: `. The 401 and 403 are the standard mapping (no Core with auth was
  started for this review). Those differences are in the docs of `query_sql/3`, not hidden. `Client.HTTP`
  passes `resolve_timeout/2` (the call's, else the connection's) to Flight. `build_ticket/2` and
  `build_ticket_payload/2` stay: they are public and documented.
- **Client.HTTP / QueryParams / facade.** `resolve_finch/1` returns `{:ok, name} | {:error, :no_pool_name}`;
  `do_request/6` and the streaming producer rescue `ArgumentError` (`unknown registry` is `:no_pool`) as
  they rescued `RuntimeError`. `encodable/2` rescues what `json_body/1` rescues. `query_span` answers
  `{:invalid_connection, term}` for a connection that is neither a keyword list nor a map. `format: nil`
  is `:json` for SQL and InfluxQL.
- **Local.** The fallback clause of `unescape_v2/3` continues with the binary after the backslash, which
  is a sub-binary and copies nothing.

## Second half

The first half (above) fixed Flight, the line-protocol escapes and the raises in `Client.HTTP`.
This half is the rest of the non-query library: the `BatchWriter` (F3's writer part, F4, F5), the
connection (F7, F11) and the refactors (F12). Each finding was re-read in the code at `bb07f89`
before it was changed.

### F3 (writer part): payloads that are not a binary or a Point killed the writer

`BatchWriter.write(w, [point])`, `write(w, iodata)` and `write(w, nil)` had no clause in the
writer's encoder: a `FunctionClauseError` killed the writer (and with it the buffer) and exited the
caller. `write/3` and `write_sync/3` now prepare the payload in the *caller*: a binary as it is,
iodata as its text, a Point or a list of Points encoded, anything else
`{:error, {:invalid_payload, payload}}`. The server-side clause for a payload that is no binary
(someone calling the `GenServer` directly) gives the same error. Encoding a Point needs two values
only the writer knows (the flushes' `:precision` and the connection's `api_version`), so the caller
asks the writer for them in one cheap call; the writer no longer encodes. This is what
`2026-09-26_batch-writer-shutdown.md` said it did ("encoded in the caller") and what a later change
had moved back into `handle_call`.

### F4: one classifier, and a capped backoff

Only a `%{status: 4xx}` was permanent; every other `{:error, reason}` was retried, so a connection
with no database retried `{:error, :no_database_specified}` `max_retries` times with growing
delays, as did every error from this side (`{:invalid_*, _}`, `{:unencodable_body, _}`,
`{:invalid_options, _}`). The retry handler and the first attempt each had their own copy of the
case. `classify/1` is the only one: `:ok`, `:retryable` for `{:connection_error, _}`,
`:pool_timeout`, `:timeout`, 5xx, 408 and 429, and `:permanent` for everything else. The backoff
`base * 2^attempt` was uncapped (attempt 20 at a 100 ms base is 29 hours); `:max_retry_delay_ms`
(default 30 s, `NimbleOptions`-validated, documented) caps it before the jitter. A huge `attempt`
no longer builds a huge integer (the exponent is clamped at 62).

### F5: the writer's mailbox

Each attempt ran `Writer.write` inside the callback. `stats/1` (5 s call timeout) exited against a
server that took longer, `write/3` and `flush/2` queued behind the request, and with `batch_size: 1`
a `write/2` blocked its caller until the request completed. (The first half already had to give the
tests that answer their own server an owner process, for the same reason.)

The design, keeping the ordering and the retry semantics:

- Every flush becomes a *chain* (its bytes and the `write_sync/3` caller to answer), as the batches
  that failed once already were. An attempt at a chain is a *job* on a FIFO queue; at most one job is
  in flight, so requests go out one at a time and oldest batch first, as they did when the
  callback made them.
- The request runs in a `spawn_monitor`ed process (no link: nothing it does can kill the writer; a
  crash in the client is the `DOWN` message, `{:error, {:write_crashed, reason}}`, a permanent
  error). It sends `{:attempt, ref, result}`; the writer handles that as an ordinary message,
  classifies it, and either ends the chain, or sets the retry timer (`{:retry, chain, attempt}`, as
  before) which enqueues the next attempt.
- Automatic flushes (batch size, timer) wait while any chain exists (in flight, queued or in
  backoff), the backpressure of before; chains now exist from the first attempt, not only after the
  first failure. Explicit `flush/2` and `write_sync/3` take the buffer at once and wait their turn.
- `flush/2` answers when its batch's first attempt has finished, as documented. With an empty buffer
  it answers when the jobs ahead of it have (a *barrier* on the queue), at once when none is in
  flight: a caller can wait for the writer to have handled the answers to what it has written.
- `terminate/2` waits for the request in flight, settles its chain by its answer (a retryable
  failure leaves the chain to be written once more, as before), then writes the chains still to be
  retried, oldest first, and the buffer, once each. Callers still waiting for a first attempt are
  answered last. The final writes do not update the stats: nothing can read them after `terminate/2`
  returns (documented).
- `stats/2` takes a timeout, 5 s by default, and answers while a request is in flight.
- `:hibernate` after every timer tick forced a full garbage collection each `flush_interval_ms`; it
  is dropped.
- `buffer_size` counts lines (the newlines of a payload, one more for the last line), so
  `batch_size` and the `10 *` bound bound the body of a flush. One write is never split, so a flush
  may hold the lines of the write that crossed the bound; documented.
- A retry re-sent an untimed point, which the server stamps with its own clock. Verified on Core
  3.10.1: `fxi31m,t=a v=1i` written twice is **2** rows, `fxi31s,t=a v=1i 1700000000000000000`
  written twice is **1** row. A server that committed a write that then timed out would therefore
  store the retried point a second time. A Point without a `:timestamp` is stamped in the caller, at
  the call, with `DateTime.utc_now/0` (one time for the whole call, as a server gives the lines of
  one request); the encoder writes it in the writer's precision. Pre-encoded line protocol cannot be
  stamped without parsing it and is still the server's to stamp. The change of behaviour is in the
  CHANGELOG under Changed.

### F7: the writer was unreachable, a Point was not a body, a name was not a connection

- `InfluxElixir.write_batched(name, payload, opts)` (`:sync`, `:timeout`) is the public way to the
  connection's writer; `flush/2` and `stats/2` share one `with_batch_writer/2`, which also maps a
  writer that stops between the lookup and the call to `{:error, :no_batch_writer}`. README and the
  testing guide describe it (the guide's example was run against `Client.Local`).
- `InfluxElixir.write(conn, %Point{})` was `{:error, {:invalid_body, %Point{}}}`. `Writer.write/3`
  encodes a Point or a list of Points with the call's `:precision` and the connection's
  `api_version` (`Connection.api_version/1`); the facade passes the payload through.
- `Writer.write(:name, ...)` raised in `Access.get(:name, :database)`: a `BatchWriter` started with
  `connection: :name` crashed on its first flush. `Writer` resolves a registered name on every call
  (so the writer follows a re-registration); an unregistered one is `{:error, {:invalid_connection,
  name}}`, a permanent error to the writer.

### F11: the connection supervisor

- `{:ok, conn} = client.init_connection(config)` raised a `MatchError`. A supervisor's `init/1` has
  no error return (anything but `{:ok, _}` and `:ignore` becomes `{:bad_return, _}`), but a process
  that exits during init is `{:error, reason}` from `start_link`: `init/1` exits with
  `{:shutdown, {:init_connection, reason}}` (no crash report) and `start_link/1` hands back
  `{:error, reason}`. Under `Supervisor.start_child/2` OTP wraps it as `{reason, child}`.
- `Connection.put` is still taken before the children start (it must be, inside the registered
  process, so two concurrent adds of one name stay atomic). The window in which a caller resolves
  the name and no pool is up is harmless: `Client.HTTP` maps the missing pool to
  `{:error, {:connection_error, :no_pool}}` (checked with a connection naming a pool that is not
  running), and the facade's batch-writer calls answer `:no_batch_writer`.
- Nothing erased the `persistent_term` entry when the supervisor stopped by itself. A first child,
  `ConnectionSupervisor.Registration`, traps exits and in `terminate/2` erases the entry and calls
  the client's `shutdown_connection/1`; it stops last (children stop in reverse start order), after
  the writer's final flush. `remove_connection/1` keeps its own release for a start that failed before
  the children (the function is one `release_connection/1`, shared). The supervisor waits for a
  predecessor's `Registration` to be gone, like the other names, so a restart does not have it erase
  the new registration.
- A failed start returned the whole config in the error tuple and logged it. Supervisors print the
  child spec's start arguments and the arguments of `init/1` in failure reports, so the token now
  travels as a `Secret`: a struct holding a **closure** over the token, with `Inspect` showing no
  field. The closure matters: Erlang's `~p` (supervisor and crash reports) prints a struct's fields
  and not through the `Inspect` protocol, but prints a function without what it captured.
  `ConnectionSupervisor.child_spec/1` and `start_link/1` wrap it; `init/1` unwraps it. The writer is
  started with `connection: name`, so its child spec holds no config. `Config`'s `:token` is still a
  binary, and the registered connection holds the binary (checked: a request through a connection
  added with a token carries `Authorization: Bearer <token>`; the error and the logs of a start that
  failed hold no token).
- `Connection.finch_name/1` always derived the name; it returns a registered connection's
  `:finch_name` when it has one.
- `Writer` split every body on newlines to fill `point_count`, with or without a handler;
  `:binary.matches/2` counts them without allocating. A blank line in the middle of a body now counts
  as one more line than before (a trailing newline still does not).

### Tests

All through the public API (`BatchWriter`, `Writer`, the facade, `ConnectionSupervisor` through
`add_connection/2`), none against a mock. The `BatchWriter` tests that read stats or storage right
after a write that completed a batch now `flush/2` first (the empty-buffer flush is the barrier);
